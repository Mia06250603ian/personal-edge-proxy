### 0.2b 判定：是线路本身，不是 IP 被针对

用户已明确回答（问了不止一遍，**不要再问第四遍**）：**白天晚上一样**。
即 358ms / 50% 丢包是这条线的**全天候常态**，不是某个时段的峰值。

延迟全天 300ms+ 而新加坡物理上跑不出这个数 → **包一直在排队** → 路堵或绕。
**排队排除了"被人为丢包"（QoS 限速）**：限速型干扰直接丢包，不会制造排队延迟。

→ **是线路/路由本身的问题。**

因此下面这些全部关闭，不要再提：

- **换 IP 无用**：同一条路由、同一个国际出口，新 IP 一样排队
- **WARP 无用**：它治"出口 IP 被目标站拒绝"，不治丢包
- **服务器上没有可调的了**：负载 0、出口 0% 丢包、参数已调完

### 0.3 这里其实是**两个问题**，不要混成一个（我犯过这个错）

| | 问题一：慢、丢包 | 问题二：彻底卡死 |
|---|---|---|
| 范围 | 全天候，**iPad 走家用 Wi-Fi 也一样**，与 5G 无关 | 只在手机 5G 上，偶发 |
| 证据 | 358ms / 50% 丢包，实测 | 三次故障，必须开飞行模式才恢复 |
| 成因 | 线路/路由本身，证据够硬 | **未定案** |

**线路差解释不了问题二。**一条堵的路会让你慢、让你卡，但**不会因为开了飞行模式就通**
——飞行模式改变不了新加坡到国内那段国际链路的拥堵。

**而且第三次 VLESS 也死了**，所以"VLESS 存活 → 手机承载是好的"这个证据不能再用。
两个不同协议、不同端口一起死，且要**重新附着网络**才恢复，这是**承载层**的特征，
不是单条连接的特征 → 指向手机与运营商之间那一段，不是服务器那一段。

**给下个会话：不要拿问题一的结论去宣布问题二解决了。**用户一开始问的是问题二。

**问题二目前唯一干净的判别器**（用户愿意配合时才提，别催）：
卡死的当下**先别开飞行模式**，用手机 SSH 连服务器 **22 端口**（不走代理）。
连得上 → 代理这条路被挡；连不上而普通网站正常 → 整个 IP 在该蜂窝上不可达；
什么都不通 → 手机承载问题，与服务器无关。

### 0.4 已被这一轮排除的（除了 §3 那些）

| 怀疑 | 排除依据 |
|---|---|
| 5G NAT 空闲超时 | 客户端默认 `keepAlivePeriod: 10s`，映射每 10 秒被刷新，盖住了所有现实 NAT 超时；且连接是在有包在走的时候死的 |
| 加 keepalive 能治 | 它已经在跑了（10s），再加只是让本来就没触发的机制更没机会触发 |
| 换服务器 IP | 见 §0.2b：延迟全天 300ms+ 说明包在排队，新 IP 走同一条路由、同一个国际出口，一样排队 |
| 深夜高峰拥塞 | 用户明确说**白天晚上一样**，故障与时段无关 |
| IP 被 QoS 限速 | 限速型干扰是直接丢包，**不会制造 250ms+ 的排队延迟** |
| 距离太远 | 新加坡比美国近得多，物理上跑不出 358ms |
| 服务器过载/缓存打满 | `load average 0.00`，服务全程 active，`UdpSndbufErrors 0` |
| 出口 IP "脏" / 包 WARP | 脏 IP 的表现是被目标站风控（验证码、封号），**不会造成丢包和连接猝死**。WARP 治不了拥塞 |

## 1. 硬约束（违反任何一条都会造成实际损害）

1. **一次只发一条短命令。** 禁止多行脚本、禁止 heredoc、禁止长 `printf`。
   用户的 iOS SSH 客户端会在粘贴的行内**静默插入和吞掉空格**，已经因此把
   YAML 写成 `password:密码`（少一个空格，类型就从映射变成字符串，而且不报错）。
2. **占位符只能用纯 ASCII 字母数字下划线**（`PASTE_XXX`）。
   **绝对不要用 `<` `>`** ——那是 shell 重定向，上一轮因此把占位符文本写进了配置。
   更好的做法：**让脚本自己 `openssl rand -hex 16` 生成并打印**，用户不用改任何东西。
3. **重启服务之前先 `grep` 验证写进去的内容**，确认冒号后面有空格。
4. **不要让用户在手机上切代理去测试。** 用户手机挂在旧机场上，切换会让已登录的
   账号看到不同的出口 IP，这是真实代价。**iPad 是唯一可以随便测的设备**
   （它本来就走这个节点，出口 IP 不变）。
5. **不要把断线次数直接念给用户听。** 短于 5 分钟的重连是锁屏/切后台，不是故障。
