# HY2 断线排查 + 安全审查

针对你那台节点（IP 见你自己存的交接单，本文一律不写真实地址）的两个问题：**为什么老是断**，**代码和线上有什么漏洞**。

审查日期 2026-09-06。审查对象是仓库里的脚本，以及这些脚本在服务器上生成的配置。
**没有登录过服务器**——所有"线上"结论都是从脚本必然生成的配置推出来的，
需要在机器上实测确认的地方都标了出来。

---

## 一、为什么老是断

### ⚠️ 实测证据修正了下面的排序（2026-09-06 追加）

初版把服务端那三个默认值列为主因。两条实测反馈把这个判断改了：

| 观察 | 排除了什么 |
|---|---|
| **TCP 8443 一直稳定** | 两条入口同机器、同出口，只差 UDP/TCP。服务器宕机、服务崩溃、流量超额、磁盘满、机房路由、密码错——**全部排除**，这些会让两条一起挂 |
| **只重开客户端没用，必须切网络才恢复** | 重开会建一条全新连接（新连接 ID、新源端口、状态全清）。它没解决问题 → **空闲超时、NAT 映射超时、连接状态卡死、Brutal 的单连接自毁，全部排除**——这些都会被新连接重置 |

两条合起来，剩下唯一自洽的解释：**中间设备按「源 IP → 服务器 UDP 端口」
拦截，且拦截扛得过新连接，只有换源 IP（切网络）才解除。**

**这不是服务器的问题，是路径上的拦截。** 相应地：

- 成因 1（`maxIdleTimeout` 30s）**基本可以划掉**——新连接会重置它，
  而重开客户端没用。设置本身仍然值得改，但它不是这次的病根。
- 成因 2（Brutal）**升级为最可能的诱因**。它不是拦截的机制，而是**招来
  拦截的原因**：按 150 Mbps 硬发且无视丢包，这条流又快又持久又丢包，
  中间设备一眼就能认出"这不是正常上网"。TCP 从不这么发，所以 TCP 没事。
  **这解释了为什么偏偏只有 HY2 被拦。**
- 成因 3（UDP 缓冲区）值得改，但同样不是病根。

**处理顺序因此变成**：

1. `bash scripts/tune-hy2.sh` —— 关掉 Brutal，把"靶子"拆掉。客户端不用动。
2. 还拦 → `bash scripts/tune-hy2.sh --enable-obfs` —— 让它根本不像 HY2。
   ⚠️ 硬切换，两台客户端要同步加同一个混淆密码，**动手前先切到 TCP 入口**。
3. 还拦 → 端口跳跃（成因 4 第 3 条）。
4. 都不行 → TCP 备用入口，它不受 UDP 限制影响。

---

### 先说结论

断线有五个可能的成因。**其中三个在服务端，是配置默认值造成的，已经修好了**；
另外两个在客户端到服务器这段路上，服务端修不了，只能绕。

先跑一遍体检，它会直接告诉你是哪一类：

```bash
bash scripts/diagnose-hy2.sh
```

然后修掉服务端的三项（客户端不用动，现有配置不会失效）：

```bash
bash scripts/tune-hy2.sh
```

---

### 成因 1：空闲超时只有 30 秒 ⭐ 最可能

Hysteria2 的 `quic.maxIdleTimeout` **默认 30 秒**。超过 30 秒没收到客户端的
UDP 包，服务端就把这条连接判死。

而 `install-hy2-official.sh` 生成的配置里**根本没写这一项**，所以一直在用默认值。

30 秒有多短：

- 手机从一个基站切到另一个基站
- 锁屏后系统压制后台网络
- 进电梯 / 地铁 / 停车场
- Wi-Fi 和 5G 之间来回切

任何一件事都能轻松超过 30 秒。这就是"信号明明满格，它自己断了"的来源。

日志里长这样，`docs/mobile-quickstart.md` §6.3.5 已经抓到过：

```text
INFO  client connected     {"addr":"CLIENT_IP:20181"}
WARN  TCP error            {"error":"timeout: no recent network activity"}
INFO  client disconnected  {"error":"timeout: no recent network activity"}
```

`no recent network activity` 就是这个超时在说话。

**已修**：放宽到 60 秒。`tune-hy2.sh` 可以用 `--idle 90s` 调更宽。

> 放宽超时不会有安全或性能代价。它只影响"多久之后认定对方掉线"，
> 连接活着的时候行为完全一样。

---

### 成因 2：客户端那句 `down: 150 Mbps` 在服务端引爆了 Brutal ⭐ 最可能

这一条最反直觉，也最值得看。

`docs/mobile-quickstart.md` 和 `examples/` 里的客户端配置都写了：

```yaml
up: "30 Mbps"
down: "150 Mbps"        # sing-box 里是 down_mbps: 150
```

看起来像是"告诉客户端我家宽带多快"。**不是的。** 这两个值会发给服务端，
而服务端一旦收到，就会从 BBR 切换到 **Brutal 拥塞控制**。

Brutal 的设计目标就是：**按你报的速率硬发，故意无视丢包**。它把丢包当成
"链路噪声"而不是"发太快了"的信号。

于是在手机上：

| | |
|---|---|
| 你报的 | 150 Mbps |
| 实际能跑的 | 30 Mbps（还会随信号波动） |
| 服务端行为 | 一直按 150 Mbps 发 |
| 结果 | 120 Mbps 全变成丢包，重传把链路彻底压垮 |
| 你看到的 | 先卡住 → 转圈 → 断 |

而且持续的高速率 UDP 恰恰是运营商 QoS 最容易识别的特征，所以它还会
**顺带招来成因 4**。两件事叠在一起，就是"时好时坏、说不清什么规律"。

服务端的 `ignoreClientBandwidth` 默认是 `false`，也就是"听客户端的"。
生成的配置里同样没写这一项。

**已修**：服务端设 `ignoreClientBandwidth: true`，从此不听客户端报的带宽，
一律用 BBR 按实际链路自适应。

> 客户端那两行现在已经不起作用了，可以留着。但建议顺手删掉或改成接近
> 真实带宽的值，免得以后重建服务端时又踩一次。

---

### 成因 3：UDP 接收缓冲区只有 208 KB ⭐ 高速时必现

Hysteria2 底层是 quic-go。quic-go 需要约 **7.5 MB** 的 UDP 接收缓冲区，
而 Ubuntu 的 `net.core.rmem_max` **默认只有 208 KB**，差了 36 倍。

缓冲区满了之后，**内核直接丢弃新到的 UDP 包**——不是网络丢的，是你自己
服务器丢的。表现是：平时还行，一开始下载大文件或看高码率视频就卡死，
然后整条连接断掉。

quic-go 启动时会在日志里抱怨这件事（`diagnose-hy2.sh` 会去找这行）：

```text
failed to sufficiently increase receive buffer size
(was: 208 kiB, wanted: 7168 kiB, got: 416 kiB)
```

`harden-server.sh` 调了 BBR，但 BBR 只管服务器出去访问网站那段 **TCP**，
跟 HY2 的 UDP 隧道完全无关（脚本自己的注释也是这么写的）。UDP 缓冲区
没人管过。

**已修**：`net.core.rmem_max` / `wmem_max` 提到 16 MB。

---

### 成因 4：运营商在限制 UDP（服务端修不了）

裸 QUIC 的流量特征很明显，部分移动网络会对它限速或干脆丢包。

**怎么确认**：`diagnose-hy2.sh` 显示服务器全部正常、握手也成功，
但断线集中在空闲超时上——那就是包在路上没了。

⚠️ 判断时守住 `AGENTS.md` §0.5 的那条规矩：**一次只改一个变量**。
"iPhone 用 5G 断、iPad 连 Wi-Fi 不断"同时换了设备和网络，说明不了任何问题。
拿同一台设备在两个网络上各试一次才算数。

**按成本从低到高绕**：

1. **换端口**。有些运营商是按端口段做 QoS 的。
2. **开 Salamander 混淆**。裸 QUIC 变成看不出协议的 UDP 流。
   服务端加 `obfs` 块，**所有客户端必须同步加同一个密码，否则全部连不上**。
   （`tune-hy2.sh` 会原样保留已有的 obfs 配置。）
3. **端口跳跃**。服务端把一整段 UDP 端口 DNAT 到 24443，客户端在这段里
   随机跳。按端口做的 QoS 会失效：
   ```bash
   iptables -t nat -A PREROUTING -i eth0 -p udp --dport 20000:50000 \
            -j REDIRECT --to-ports 24443
   ```
   客户端地址写成 `<你的节点IP>:20000-50000`。
   （规则重启会丢，要 `iptables-persistent` 才能持久化。）
4. **切 TCP 备用入口**。运营商真要掐 UDP，前三条都是绕，这条才是根治。
   你已经装好了：**8443 / VLESS+TLS**。

---

### 成因 5：NAT 映射漂移（服务端修不了）

移动网络的 NAT 映射会变。映射一变，你的公网 IP:端口就变了，服务端认不出
这还是同一条 QUIC 连接，直接断。

QUIC 本来有连接迁移机制来解决这个，但它依赖客户端实现，且在运营商 NAT
后面并不总是奏效。

**怎么确认**：`diagnose-hy2.sh` 会统计日志里客户端来源 IP 出现过几个。
**多于一个就是漂移。**

放宽 `maxIdleTimeout`（成因 1）能减少它的影响，根治同样是走 TCP 入口。

### 一张表

| 成因 | 在哪 | 修了吗 | 怎么确认 |
|---|---|---|---|
| 1. 空闲超时 30s | 服务端配置 | ✅ `tune-hy2.sh` | 会话时长普遍在 30 秒上下 |
| 2. Brutal 硬发 | 服务端配置 | ✅ `tune-hy2.sh` | 高速时丢包严重、越用越糟 |
| 3. UDP 缓冲区 208KB | 系统 sysctl | ✅ `tune-hy2.sh` | 日志里有 buffer size 告警 |
| 4. 运营商 QoS | 路上 | ❌ 只能绕 | 换网络就好 |
| 5. NAT 漂移 | 路上 | ❌ 只能绕 | 日志里客户端 IP 变过 |

**先修 1-3。** 它们是确定存在的配置缺陷，而且改动只在服务端、可回滚、
现有客户端不受影响。修完观察几天，还断再按成因 4 的四步走。

## 二、安全审查

按严重度排列。标【已修】的这次改了，标【要你决定】的需要你自己权衡。

### 🔴 高：两条入口都关掉了证书校验【要你决定】

两条入口用的都是自签证书，因此两边客户端都必须勾"跳过证书验证"：

```text
HY2        insecure=1
VLESS+TLS  skip-cert-verify: true
```

**"跳过证书验证"的含义是：客户端不检查对面到底是不是你的服务器。**

于是一个能插进你和 VPS 之间的攻击者（运营商、恶意 Wi-Fi、BGP 劫持）可以：

1. 自己签一张证书冒充你的服务器，客户端不会有任何提示；
2. **拿到你的 HY2 密码 / VLESS UUID**（它们是在 TLS 建立之后才发的，
   但 TLS 在攻击者那里终结，所以他看得见明文）；
3. 把流量转发给真服务器，**中间全程明文可读**。

VLESS 这条更糟：VLESS 在 TLS 之外没有第二层加密，TLS 一破就全裸。

现有说法（`install-hy2.sh` 的注释）说"HY2 靠密码认证，密码不会因为证书自签
而泄露"——**这句话只在被动监听下成立，在主动中间人下不成立。**

> 现实一点：针对个人节点做主动中间人的门槛不低，日常大概率不会遇到。
> 但你换掉机场的理由本来就是"不想被中间人看流量"，这个洞正好把那个
> 目标抵消掉了，所以值得修。

**修法 A（推荐，不需要域名）：证书指纹固定。**

不验证 CA，改成"只认这一张证书"。在服务器上取指纹：

```bash
# HY2 的证书
openssl x509 -in /etc/hysteria/cert.pem -noout -fingerprint -sha256
# TCP 入口的证书
openssl x509 -in /etc/sing-box/cert.pem -noout -fingerprint -sha256
```

sing-box 客户端把 `insecure` 换成内联证书（iOS 上没法放文件，用这种写法）：

```jsonc
"tls": {
  "enabled": true,
  "server_name": "www.bing.com",
  "certificate": [
    "-----BEGIN CERTIFICATE-----",
    "……把服务器上 cert.pem 的内容逐行贴进来……",
    "-----END CERTIFICATE-----"
  ]
}
```

mihomo / Clash 用指纹字段：

```yaml
fingerprint: <上面那串 sha256，去掉冒号>
skip-cert-verify: false
```

⚠️ 固定指纹之后，**服务器换证书就等于所有客户端连不上**。
（顺带一提：`add-tcp-entry.sh` 里的证书复用条件原本写反了，会在每次重跑时
换一张新证书——那个 bug 这次一并修了，见下面。）

**修法 B（更彻底）：搞个域名 + ACME 真证书。** 一年几十块，之后
`skip-cert-verify` 可以直接关掉，也不用管指纹。

### 🔴 高：SSH root + 密码登录 + 22 端口【要你决定】

你的交接单写着 `SSH root + 密码 / 22 端口`。这是整台机器上最可能被攻破的地方——
爆破 SSH 是全互联网 7×24 在跑的自动化行为。

`harden-server.sh` 装了 fail2ban，但它的策略偏松：

```ini
findtime = 10m      # 10 分钟内
maxretry = 5        # 失败 5 次
bantime  = 1h       # 封 1 小时
```

对"每个 IP 慢慢试几次、换一批 IP 再来"的分布式爆破，这个策略基本拦不住。

**建议（按性价比）**：

1. **改用 SSH 密钥。** `harden-server.sh` 末尾有完整步骤。
   ⚠️ 严格照它说的做：**先验证密钥能登录成功，再关密码登录**。
   你是纯手机运维，没有救援控制台，顺序搞反就是把自己锁在外面
   （`AGENTS.md` §0.4 特意强调过）。
2. 密钥配好之前，先把 fail2ban 调紧：
   ```ini
   findtime = 1h
   maxretry = 3
   bantime  = 1d
   ```
3. 别改 SSH 端口。挡不住针对性扫描，只会让你自己每次多记一个数字
   （脚本注释里已经解释过，这个判断是对的）。

### 🟡 中：sing-box 配置全服务器可读【已修】

`add-tcp-entry.sh` 写 `/etc/sing-box/config.json` 时没设权限，默认落到 **0644**：

```text
-rw-r--r-- root root /etc/sing-box/config.json
```

里面有 **VLESS UUID**，也就是这条入口的钥匙。服务器上任何一个非 root 用户
都能直接读走。

对比一下，HY2 那边是做对了的（`chmod 600` + `chown hysteria`），这里是漏了。

**已修**：写完就 `chmod 600`；如果 systemd 单元里指定了以非 root 用户运行，
则把属主移交给该用户（否则服务会以 permission denied 退出——
`install-hy2-official.sh` 在 hysteria 上正好踩过这个坑）。

---

### 🟡 中：UUID 被长期留在 /tmp 里【已修】

`add-tcp-entry.sh` 的自测环节把客户端配置写到固定路径：

```text
/tmp/tcp-entry-selftest.json     0644，含 UUID，脚本跑完不删
```

等于把入口钥匙抄了一份放在 `/tmp` 里长期公开可读。`/tmp/sb-selftest.log` 同理。

**已修**：改用 `mktemp -d` 建 0700 临时目录，并用 `trap` 保证退出时一定清掉
（包括报错退出和 Ctrl-C 的路径）。

---

### 🟡 中：访问日志记下了你去过的每一个网站【已修】

`install-hy2.sh` 生成的 Xray 配置开了访问日志：

```jsonc
"access": "/var/log/xray/access.log"
```

这个文件记录**每一次连接的目标域名**，永久保留，没有轮转。两个后果：

- **隐私**：VPS 被打快照、被服务商取证、或者被入侵，等于交出一份完整浏览历史。
  你自建节点本来就是为了不让别人拿到这个。
- **可用性**：不轮转的日志会写满磁盘，磁盘一满服务就异常退出——
  这本身就是"莫名其妙就断了"的一种。

`add-tcp-entry.sh` 的 sing-box 用 `"level": "info"`，也会把每条连接的目标
写进 journal（journald 会轮转，所以只有隐私问题，没有磁盘问题）。

**已修**：Xray 访问日志设为 `none`；sing-box 日志级别降到 `warn`。
错误日志都保留，排错不受影响。

> HY2 那边不受影响：hysteria 只记 `client connected` 这类连接事件，不记目标地址。
> 这些事件正是 `diagnose-hy2.sh` 排查断线要用的，所以刻意保留。

### 🟡 中：TLS 私钥被交给共享账号 nobody【已修】

`install-hy2.sh` 里：

```bash
chown -R nobody:nogroup "$CERT_DIR"
```

`nobody` 是系统上的**共享**通用低权限账号，不是专属服务账号。把 TLS 私钥交给它，
等于让任何以 nobody 身份运行的进程都能读走私钥。

**已修**：改成先问 systemd 单元里 Xray 实际配的是哪个用户，只把**私钥本身**
交给那个用户；如果是 root 运行就保持 root 属主。

### 🟢 低：真实 IP 留在了 git 历史里

你的节点真实 IP 曾经被写进 `docs/mobile-quickstart.md` 当例子，后来在
`fa8a6f2` 里换成了占位符——但**它还在 git 历史里**，横跨约 10 个 commit。

```bash
git log --all -S'<你的节点IP>' --oneline
```

仓库目前是私有的，所以现在没有实际暴露。但：

- 一旦仓库转公开，这段历史会跟着公开；
- 你自己的交接单第一行就写着"不要进仓库"。

**建议**：仓库保持私有就行，不值得为此重写历史（`git filter-repo` 会打乱
所有 commit 哈希）。**但转公开之前必须先清理。**

顺带：旧机场那个 IP 不在历史里，已确认。

### 🟢 低：用 `curl | bash` 装服务端，未固定版本、未校验

三个脚本都这么装：

```bash
bash <(curl -fsSL https://get.hy2.sh/)
curl -fsSL https://sing-box.app/install.sh | sh
bash -c "$(curl -fsSL .../Xray-install/raw/main/install-release.sh)" @ install
```

以 root 执行一段每次都可能不一样的远程代码，既没固定版本也没校验签名。
上游被入侵或域名被劫持，你的机器就跟着完蛋。

这是这类项目的通行做法，风险可接受；**记着有这回事**就行。真要收紧，
就下载对应版本的二进制并核对 release 的 checksum。

### 🟢 低：自签证书的 VLESS 入口本身就是可识别特征

主动探测 8443，会拿到一张 CN 写着 `www.bing.com`、但根本不是 bing 签发的
自签证书。这是相当明确的代理特征。

脚本选 8443 而不是 443 是对的（443 被扫得最狠，注释里的判断成立），
但这只是降低被扫中的概率，不改变被扫中之后的结论。

**要根治**：REALITY（借用真站点的 TLS 握手，探测者看到的就是真站点）。
⚠️ `AGENTS.md` §0.6 记录了 **Xray** 的 REALITY 在这台机器上起不来——
但那是 Xray 的问题，**sing-box 的 REALITY 没试过**，而 sing-box 在这台机器上
是能正常工作的。想做的话这是个明确的方向，不过要先实测。

### 🐛 顺手修掉的 bug：证书复用条件写反了【已修】

`add-tcp-entry.sh`：

```bash
openssl x509 ... -noout -issuer | grep -qv "CN *= *${SNI}"
```

`grep -qv` 是"有行不匹配就成功"。issuer 只有一行，所以这个条件在
**证书正确时为假、证书不对时为真**——正好反了：CN 对得上就重新生成，
CN 对不上反而沿用。

实际后果：不带 `--domain` 跑时，每次重跑都会换一张新证书。因为客户端勾了
"跳过证书验证"所以一直没人发现。但如果你采纳上面的**证书指纹固定**建议，
这个 bug 会让每次重跑都把所有客户端打掉。

**已修**：改成 `-subject` + `grep -q`（正向匹配），并且不再要求必须带
`--domain` 才检查。

## 三、动手顺序

```bash
# 1. 先体检，看断在哪一层（只读，不改任何东西）
bash scripts/diagnose-hy2.sh

# 2. 修掉服务端三个断线成因（可回滚，客户端不用动）
bash scripts/tune-hy2.sh

# 3. 观察几天。还断就加长窗口再看一次
bash scripts/diagnose-hy2.sh --hours 72
```

安全那边，两个"要你决定"的按这个顺序：

1. **SSH 密钥**——先验证能登录，再关密码登录，顺序不能反；
2. **证书指纹固定**——把 `insecure` / `skip-cert-verify` 换掉。

其余带【已修】的已经在脚本里改好了，重跑对应脚本即可生效
（`add-tcp-entry.sh` 会沿用现有 UUID 和证书，客户端不受影响）。
